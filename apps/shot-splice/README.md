# SHOT SPLICE

縦に分割して撮った複数枚のスクリーンショットを、重なりを自動検出して 1 枚の縦長画像に継ぎ直すツール。
モバイルでの片手操作を主想定に設計している。

画像はブラウザの外に出ない。バックエンド・アカウント・保存機能を持たず、Web フォントも含めて**ネットワークリクエストを一切発生させない**。

## 機能

- ファイル選択またはドラッグ&ドロップで **2〜12 枚**の画像を読み込む
- 隣接するショットごとに、グレースケール行差分の 2 段階探索で重なり量を自動検出
- **全ショットに共通する固定ヘッダー / フッターを自動検出**し、数値で提示したうえでカット（解除・1px 単位の微調整・「先頭と末尾もカット」への切り替えが可能）
- 継ぎ目ごとの手動調整（ドラッグ / 数値入力 / ±1・±10 ステッパー / 矢印キー）
- 継ぎ目ごとに、重なり領域でどちらのショットを前面に出すか選択
- 差分表示モード：重なり領域に 2 枚の絶対差分を描き、完全に一致していれば黒くなる
- ショットの並べ替え（ボタン / 長押しドラッグ）と削除
- 出力サイズ・重なり量・一致度のリアルタイム表示
- PNG 書き出し

## 自動検出アルゴリズム

2 枚をグレースケール化し、重なり領域の行差分の平均が最小になる重なり量を探す。

1. **粗探索** — 幅だけを 100px 相当に縮小した（**高さは原寸のままの**）グレースケール画像で、候補となる重なり量を走査する。1 候補あたりの比較行数には上限を設け、超える場合は行を**等間隔に間引く**。
2. **精密探索** — 粗探索の最良候補の近傍だけを、フル解像度・全行・1px 刻みで再評価する。

### なぜ「高さを縮小しない」のか

スクリーンショットの真の継ぎ目は、**1px ずれただけでコストが跳ね上がる鋭いスパイク**として現れる。
高さ方向に縮小すると隣接行が平均化され、このスパイクが周囲へ滲んで探索が別の位置を指す。
前身のプロトタイプ（`shot-splice-grid`）で実際に起きた不具合で、本実装ではこれを設計上の制約として固定している。

高速化に使ってよいのは**幅の縮小**と**行の間引き**だけ。間引きは平均化と違い、1px ずれれば比較対象の行の内容そのものが入れ替わるため、スパイクが保存される。
この制約は単体テスト（`tests/core/alignment.test.ts` の AC-104）で恒久的に固定してある。実際に高さも平均する実装で同じ条件（重なり 1200px）を試すと、正解 1200 に対して 148 を返す。

### 固定ヘッダー / フッターの検出

全ショットを基準幅に揃えたうえで、上端・下端から内側へ走査し、全ショット間で一致しなくなった行で止める。
上限は最短ショット高さの 25% に固定してある。これがないと、同一の画像や単色のスクリーンショットで「画像全体が共通帯」と判定され、すべて消えてしまう。

**検出結果を無言でカットすることはない。** アプリは元画像のコピーを持たないため、自動カットは取り消せない操作になる。必ず数値として提示し、オフにでき、上書きできるようにしている。

## 設計上の制約

`src/core/` は **DOM にも Canvas にも依存しない純粋関数だけ**で構成する。

jsdom には Canvas 2D の実装がないため、`CanvasRenderingContext2D` を直接名指しした時点でそのモジュールは単体テスト不能になる。
Canvas に触れるのは `src/imaging/` だけで、そこでも実際に呼ぶメンバーだけを並べた構造的部分型（`CanvasLike` / `Ctx2DLike`）に依存させ、テストでは記録用のフェイクを渡せるようにしてある。

```
src/
├── core/     純粋関数（重なり検出・共通帯検出・レイアウト計算・一致度の等級付け）
├── imaging/  Canvas 依存（ラスタライズ・合成・継ぎ目の切り出し）
├── ui/       DOM（状態・各コンポーネント）
└── main.ts   配線
```

## スタイル方向

**SPLICE BAY — 編集室のスプライサー**。フィルムを物理的に繋ぐ編集機材の質感を、iOS のマテリアル感で再構成した。

- **配色は情報チャネルであって装飾ではない。** シアン `oklch(80% 0.13 183)` = 一致、アンバー `oklch(80% 0.14 76)` = ずれ。一致度に応じて 2 色を oklab 空間で連続補間し、継ぎ目のレール・バー・ラベルの色に反映する。この 2 色は継ぎ目の状態表現に予約してあり、他の用途では使わない
- **地はほぼ黒だが純黒にしない**（`oklch(15.5% 0.014 264)`）。スクリーンショットには黒が含まれるため、扱っている素材と UI が区別できる必要がある
- **書体はシステムフォントスタックのみ。** フォントファイルをバンドルせず、Apple 端末では実際に San Francisco が表示される。数値は等幅＋`tabular-nums` で、ドラッグ中に桁が揺れない
- **数値が主役の階層。** 本文 15px に対し重なり量の readout は 40px 相当
- **ショットと継ぎ目を 1 本の縦リールに織り交ぜる。** 厚いショット行と薄い継ぎ目行が交互に来るリズムが、均一なカードグリッドを崩す。サムネイル列を貫く縦線が、ショットが 1 本に繋がっていることを示す
- **プレビュー背後のウォッシュは、読み込んだ画像の平均色から生成する。** 固定の装飾グラデーションと違い、扱っている素材に画面が呼応する

## 開発

```bash
npm install

```

### ブラウザでの検証

「CSS にそう書いた」と「実際にそう見えている」は別物なので、レンダリング結果を数値で測る検証スクリプトを常設している。

```bash
npm run build
npm run preview -- --port 4179 --host 127.0.0.1 &
npm run verify
```

- `scripts/make-fixtures.mjs` — **正解が構成上わかっている**テスト画像を生成する。1 枚の長いページを作り、各ショットをその窓として切り出すので、重なり量は近似ではなく厳密に既知になる
- `scripts/verify.mjs` — 検出精度・差分表示・PNG 書き出しに加えて、ヘアラインのコントラスト比、UI 部品への line-height の継承、タップターゲットの実寸、タイポグラフィのスケール差、一致度の色補間を実測する。横スクロールの有無は Chromium / WebKit / Firefox の 3 エンジン × 7 幅で確認する
- `scripts/verify-flows.mjs` — 枚数上限・ドラッグ&ドロップ・読めないファイル・重なりなし・並べ替え・帯カットの各経路と、検出時間の実測

`playwright` は devDependency だが、この検証スクリプトからしか使わない。Docker イメージでは `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` を立ててブラウザを取得しないようにしてある。

## Docker

```bash
docker build -t shot-splice .
docker run --rm -p 8080:80 shot-splice
# http://localhost:8080
```

`dist/` を `nginx:alpine` で配信するマルチステージ構成。

## 技術スタック

Vite + TypeScript + 素の CSS。UI フレームワークは使っていない。画面が 1 枚で状態も浅く、画像処理は Canvas 2D だけで完結するため、フレームワークを入れる利点よりバンドルサイズの増加が上回ると判断した（現状 JS 約 13KB gzip）。
