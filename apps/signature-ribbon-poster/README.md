# Signature Ribbon Poster

マウス・タッチ・ペンで描いた署名や一筆書きを、動かした速度に応じて太さと発光の強さが変わる「リボン」の光跡として暗い背景に描き、キャプション付きの一枚のポスターとして書き出すツールです。

すべての処理はブラウザ内で完結し、サーバーへのデータ送信は一切行いません。

> app-factory パイプラインが生成したプロトタイプを土台に、本実装として作り直したものです。仕様は [`docs/SPEC.md`](docs/SPEC.md)、設計は [`docs/PLAN.md`](docs/PLAN.md)、作業単位は [`docs/TASKS.md`](docs/TASKS.md) を参照してください。

## 特徴

- Pointer Events でマウス／タッチ／ペンいずれの入力にも対応。描き足して1枚に複数ストロークを重ねられます。
- 移動距離とタイムスタンプから瞬間速度を算出し、直近5サンプルの移動平均で平滑化。**遅い動きほど太く濃く強く発光し、速い動きほど細く淡く弱く発光**します。
- 速度と見た目の対応の強さを **Response** スライダー（Calm / Balanced / Volatile）で調整できます。変更は既に描いたストロークにも遡って反映されます。
- 背景は「Noir / Midnight Navy / Deep Bordeaux」の3プリセット、リボンの発光色は「Gold / Ice Blue / Crimson / Pearl / Emerald」の5色。色は**ストローク単位**で保持されるので、1枚の中に複数色を混ぜられます。
- Undo / Redo / Clear（Clear も Undo で戻せます）。`Cmd/Ctrl+Z`・`Cmd/Ctrl+Shift+Z` のショートカット付き。
- 任意の一行キャプション（署名者名・日付など）を入力すると、書き出し時にポスター下部へセリフ体で焼き込まれます。未入力なら一切描画されません。
- 書き出し解像度を **Study（900×1273）/ Edition（1800×2545）/ Archival（3600×5090、300dpi で約 A3）** から選べます。解像度が変わっても構図は変わりません。
- 制作中の内容は自動でローカル保存され、次回起動時に**復元するかどうかを選べます**（自動では復元しません）。

## 使い方

```bash
npm install
npm run dev            # 開発サーバー
npm run build          # 型チェック + 本番ビルド（dist/ に出力）
npm run preview        # ビルド済み dist/ をローカルでプレビュー

npm test               # 単体・統合テスト
npm run test:coverage  # カバレッジ（行/分岐/関数 80% 未満で失敗）
npm run test:e2e       # Playwright による E2E
npm run bench          # 描画性能の新旧比較（後述）
```

1. 右側パネルで背景色・リボンの色・Response を選びます。
2. キャンバスをマウス・タッチ・ペンでドラッグして署名／一筆書きを描きます。
3. 必要なら Signature Line に一行キャプションを入力します。
4. Resolution を選び、「Download Poster」で PNG を書き出します。

## 技術スタック

Vite + TypeScript（フレームワークなし）。描画は Canvas 2D API を直接利用し、外部の描画ライブラリには依存していません。バックエンドはありません。

```
src/
├── core/     純粋ロジック（DOM / Canvas 非依存・ブラウザ無しでテストできる）
├── render/   Canvas 描画層（最小インターフェース経由なのでフェイクで駆動できる）
├── app/      状態・入力・書き出し・UI 部品
└── main.ts   配線のみ
```

## 描画性能

プロトタイプは、リボンを **セグメントごとに `shadowBlur` 付きで3パス**、**1800×2545 固定**のバッキングストアへ、ドラッグ中は**毎フレーム全ストローク再描画**していました。`shadowBlur` は描画呼び出しごとにぼかしを走らせるため、点数が増えるほど急激に重くなります。

本実装では次のように作り替えています。

| | プロトタイプ | 本実装 |
|---|---|---|
| ぼかし処理の回数 | セグメント数 × 3 | フレームあたり数回（レイヤー単位） |
| ドラッグ中の描画対象 | 常に全セグメント | 新しく確定したセグメントのみ |
| バッキングストア | 1800×2545 = 4,581,000px 固定 | 表示サイズ依存（520px 幅表示で 382,200px、**約 12 分の 1**） |

発光は `shadowBlur` ではなく、**ボディ層を縮小・ぼかして加算合成し直す多段ブルーム**で作ります。コストがセグメント数から独立するうえ、単一半径のぼかしより falloff が滑らかで広いハローが得られます。

### 計測結果

`npm run bench` は、プロトタイプの描画コード（`bench/legacy-renderer.ts` に当時のまま保存）と本実装に**同一のストローク**を描かせて比較します。以下は Apple M1 / Chromium（GPU 有効）/ 表示幅 520px での中央値です。

| 点数 | 本実装: 1点追加 | 本実装: 全再描画 | プロトタイプ: 全再描画 |
|------|----------------|-----------------|----------------------|
| 200 | 0 ms | 0.4 ms | 1.1 ms |
| 500 | 0 ms | 0.9 ms | 2.3 ms |
| 1000 | 0 ms | 3.6 ms | 6.0 ms（ただし下記） |

**中央値より重要なのは、プロトタイプに間欠的な長時間ストールがあることです。** 1000点の5回の計測は `6.0, 6.3, 3571.5, 4.8, 4.4` ms で、1回だけ **3.5 秒** かかっています。GPU を無効にした環境（ヘッドレス Chromium）では、1000点でこのストールが常態化し 40〜50 秒に達しました。描画呼び出しが増えると Chromium の canvas がソフトウェア描画に落ちるためと考えられます。本実装ではこのストールは発生しません。

**この数値の読み方**（正確を期すための注意）

- Canvas の描画命令は GPU に積まれるため、`performance.now()` の差分には GPU 側の実行時間が完全には含まれません。新旧どちらの値も実際のコストを過小評価しています。上表は絶対値ではなく**相対比較**として読んでください。
- 「1点追加 0 ms」はタイマー分解能を下回っているという意味です。ゼロコストではありませんが、**ストロークが何点になっても一定**であることが重要な点です（プロトタイプは1点増えるたびに全体を描き直すため、点数に比例して増えます）。
- 計測は M1 Mac 1台のみの結果です。他のハードウェアでの比率は異なります。

### 質感を落としていないことの確認

軽量化と引き換えに安っぽくならないよう、新旧を同条件で描画し、**輝度帯ごとの平均色と彩度を実測**して比較しています（目視だけでは「白飛びしてゴールドが失われる」種類の劣化に気づけないため）。

| 輝度帯 | プロトタイプ | 本実装 |
|--------|-------------|--------|
| 30–60 | rgb(54,42,19) 彩度 65% | rgb(43,35,19) 彩度 56% |
| 60–100 | rgb(96,75,32) 彩度 67% | rgb(98,78,39) 彩度 60% |
| 100–160 | rgb(161,126,54) 彩度 66% | rgb(162,129,61) 彩度 62% |
| 160–220 | rgb(233,187,83) 彩度 64% | rgb(241,195,90) 彩度 63% |

開発中、この計測でハローの彩度が 36% まで落ちていた（＝ゴールドが灰色に脱色されていた）ことが見つかり、次の2点を修正しています。

1. レイヤー内部の加算合成をやめた。セグメント接合部の丸端が重なる箇所で白に飽和し、その層をぼかして作るブルームまで白っぽくなっていたため。加算は**層同士を重ねるときだけ**に限定した。
2. 白寄りのホットコアをブルームの生成元から外した。ボディ層（純粋な選択色）とハイライト層に分け、ブルームはボディ層のみから作る。

## Docker での起動

```bash
docker build -t signature-ribbon-poster .
docker run --rm -p 8080:80 signature-ribbon-poster
# http://localhost:8080
```

静的ビルド成果物を nginx で配信するだけのマルチステージ構成です。

## デザイン方針

ダークラグジュアリー。ほぼ黒の地にゴールド（`#c9a24b`）1色のアクセントとパールの文字、細いヘアライン罫線、Playfair Display × Cormorant Garamond のセリフ体で、ギャラリーのキャプションカードのような佇まいにまとめています。装飾のための色は足さず、キャンバス上で発光するリボンそのものが視線を集める主役になるようにしています。

追加した UI（Response スライダー、Resolution セレクタ、復元バナー、トースト）も、ブラウザ標準の見た目をそのまま出さず、既存のヘアラインとゴールドの下線モチーフを流用しています。すべてのアニメーションは `prefers-reduced-motion: reduce` を尊重します。

## スコープ外

- SVG 等ベクター形式での書き出し（グロー表現がラスター前提のため）
- 筆圧（pressure）・傾き（tilt）による追加の線幅制御
- 自由なカラーピッカー、グラデーション軌跡、複数色の混色
- キャプションの詳細カスタマイズ（フォント・位置・サイズ・複数行）
- サーバー保存・共有リンク・ギャラリー・アカウント機能
- キャンバスのズーム／パン — 検討のうえ不採用。中核体験が「一筆を止めずに描き切ったときの速度の連続性」にあり、パンを挟むとポインタ移動が分断されて抑揚が壊れるため。ポスターは画面に全体が収まる縦長1枚なので、拡大しないと描けない場面も構造的に存在しません（詳細は SPEC の FR-015）
- スマートフォン向けの最適化（PC・タブレット利用を主対象。レイアウトは破綻させません）

## 既知の制約

- `ctx.filter` 非対応の環境（Safari 17 未満など）では、ブルームが縮小・拡大の双線形補間のみになり、halo がわずかに硬くなります。描画自体は成立します。
- Archival（3600×5090）の書き出しは端末によっては数秒かかります。処理中はボタンにローディング表示が出て、多重実行は防がれます。
- `localStorage` が使えない環境（プライベートモード、容量超過など）では下書きの自動保存が行われません。その場合は起動後に一度だけ通知され、以降は無音です。主要機能は通常どおり動作します。
- 性能計測は Apple M1 Mac 1台での結果です。
