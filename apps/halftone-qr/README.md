# Halftone QR

画像を網点に分解して、QR コードの模様そのものに溶け込ませるジェネレーター。
すべてブラウザ内で完結し、画像もテキストも送信されません。

姉妹アプリ `apps/qr-code-designer/` の「QR の中央にロゴを載せる」方式とは異なり、
**画像全体を QR の模様に溶け込ませる**のが本アプリの差別化点です。

---

## 使い方

```bash
npm ci
npm run dev      # 開発サーバー
npm run build    # dist/ に静的ファイルを出力
npm run preview  # ビルド結果を確認
npm test         # 単体テスト
```

`dist/` をそのまま静的ホスティングに置けば動きます（バックエンド不要）。
`base: './'` で相対パス出力にしているので、サブディレクトリ配信にも対応します。

## 仕組み

Chu et al. *Halftone QR Codes*（SIGGRAPH Asia 2013）の中核アイデアを実装しています。

1. QR コードの 1 モジュールを **3×3 のサブモジュール**に分解する
2. **各モジュールの中央サブモジュールは、元の QR のビット（黒/白）を必ず保持する**
3. 残り 8 個は自由なので、埋め込みたい画像の濃淡に合わせて誤差拡散法で塗る

中央が常に正しい値になるため、誤り訂正の対象データが保たれたまま、
全体としては画像のシルエットが見える、という仕組みです。

### 中央固定は破ってはいけない不変条件

この不変条件が崩れると手法の前提そのものが失われるため、
「QR らしさ」「保護レベル」「階調」の全組み合わせに対して
テストで全数検証しています（`src/lib/halftone.test.ts`）。

### QR らしさ（λ）

非中央サブモジュールの目標輝度を、元のモジュール値へどれだけ引き寄せるかの強度です。

```
mix    = λ·w + λ²·(1 - w)
target = 画像の輝度 × (1 - mix) + モジュールの輝度 × mix
```

`w` は位置ごとの重みで、上下左右が 1.0、斜め 4 隅が 0.55。
隅を弱めているのは、隣接モジュールと視覚的に共有される位置で、
ここを固めると画像のディテールが真っ先に失われるためです。

二次項を入れているのは、単純な `λ·w` だと λ を最大にしても斜め 4 隅が
画像に従い続け、**スライダーを振り切っても元の QR に戻らない**ためです。
現在は λ=1 で保護レベルによらず元の QR の 3 倍拡大と完全一致します。

### 読み取り判定は「実際にデコードして」行う

静的な推定ではなく、生成物そのものを **ZXing（`@zxing/library`）で実デコード**します。
解像度 3 段階 × ぼかし 3 段階の 9 条件で試し、
デコード成功かつ**内容が入力と完全一致**した場合だけ成功と数えます。

- 判定は Web Worker 上で走らせ、UI をブロックしません
- `TRY_HARDER` は付けていません。実機より甘い判定になると
  「良好」と表示したものが現場で読めない事故につながるため、保守側へ倒しています
- 判定器に jsQR を使わないのは、過去に「解像度を上げるほどデコード率が下がる」という
  実スキャン特性としてあり得ない挙動を示した実績があるためです

## 技術選定

| 領域 | 選定 | 理由 |
|------|------|------|
| ビルド | Vite 8 | 静的出力のみで完結。`base: './'` 対応 |
| UI | React 19 + TypeScript | 設定 → プレビューの単方向データフローが素直。状態が 15 個程度あり宣言的に書く利点が大きい |
| テスト | Vitest | Vite 設定を共有できる。`environment: 'node'` で純ロジックを高速に回す |
| QR 生成 | `qrcode-generator` | 生のモジュール行列だけ取れる軽量ライブラリ。描画機能に依存しない |
| 読み取り判定 | `@zxing/library` | 信頼できる QR デコーダ。Worker 内で動的 import し初期バンドルから除外 |
| 描画 | Canvas 2D（素） | 出力がビットマップなので SVG の利点がない |
| フォント | `@fontsource` 同梱 | 外部 CDN を使わない |

**採用しなかった選択肢**

- *素の HTML/CSS/JS*: 再計算の依存関係（サンプリング結果のキャッシュ、Worker 結果の
  レース制御）が多く、手書きの状態管理は割に合わない
- *zxing-wasm*: WASM 資産の追加配信が必要で静的ホスティングの手数が増える
- *OffscreenCanvas での Worker 描画*: 描画はメインスレッド、Worker には
  グリッドのみ渡す構成にして環境依存を減らした

### 機能パターンの座標判定を自前で持っている理由

ハーフトーン化ではファインダーや位置合わせパターンを画像で潰すと一気に読めなくなります。
どのモジュールが機能パターンかを知る必要がありますが、`qrcode-generator` は
役割を公開しません。そのため位置合わせパターンの中心座標表（型番 1–40）を含めて
QR 仕様の座標規則から自前で判定しています（`src/lib/qr.ts`）。

## 実装した機能

- 画像アップロード（ドラッグ&ドロップ / クリック / キーボード操作）
- エンコードするテキスト入力（UTF-8 バイトモード、日本語対応）
- 誤り訂正レベル H / Q / M（画像を載せているあいだは H に自動固定）
- ハーフトーン変換（Floyd–Steinberg 誤差拡散、蛇行走査、誤差クランプ）
- QR らしさスライダー / 機能パターン保護 3 段階
- トリミング（ズーム・水平/垂直位置）と階調（明度・コントラスト・反転）
- 変換前後の 2 面比較プレビュー（リアルタイム反映）
- ZXing による 9 条件の読み取り判定 + 改善助言
- PNG 書き出し（標準 / 高解像度 / 印刷用、出力上限 8192px）

## 既知の制約

- **書き出した PNG を等倍のままソフトウェアデコーダに渡すと失敗することがあります。**
  ハーフトーン QR はカメラの光学的なぼけ（＝縮小による平均化）を前提とする方式のためです。
  同条件で通常の QR は等倍でも読めることを実測で確認しており、この方式に固有の性質です。
  カメラで撮るか、縮小してから読ませてください。
- 読み取り判定はソフトウェアデコーダによる目安で、実際の読み取り機・印刷品質・照明までは
  再現できません。**実機でのテストは必須**です。
- **カラー画像は未対応**です（グレースケールのハーフトーンのみ）。
- 論文にある**誤り訂正符号の再エンコード最適化**（等価なコードワード候補の中から
  画像適合度が最大のものを選ぶ手法）は未実装です。実装すれば同じ λ でも
  画像の再現度を上げられます。
- 誤差拡散は Floyd–Steinberg のみで、手法の切り替えはできません。
- SVG / PDF 書き出しは未対応です（ハーフトーンは本質的にビットマップのため）。
- E2E テストはリポジトリに常設していません（検証時に一時的に実行）。

## 検証結果

- 単体テスト **111 件**通過（`npm test`）
- `npm run build` 成功。初期バンドル **77KB gzip**
  （ZXing の 454KB は Worker 側チャンクに分離され、初期ロードに含まれないことをビルド成果物で確認）
- 実ブラウザ検証（Playwright / Chromium）
  - コンソールエラー **0 件**
  - 360 / 375 / 768 / 1024 / 1440 / 1920px で横スクロールなし
  - キーボードのみで全操作要素に到達可能
  - 画像投入 → 判定表示 → PNG ダウンロードの通し動作を確認
- 書き出した PNG を**独立した経路**（別ブラウザ・ZXing UMD・実ファイル）でデコードし、
  5 段階の縮小率のうち 4 段階で入力テキストと完全一致することを確認
