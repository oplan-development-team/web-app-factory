# pipeline-log

`Workflow`ツールの実行結果はJSONの戻り値しか見えず、途中で各エージェントが何を考え・何を判断したかが追いにくい。このスキルは、パイプライン内の各エージェントが自分の作業を終えて次工程に結果を渡す直前に、簡単な活動記録を書き残すための手順を定める。

## ログ先

`.claude/logs/<パイプライン名>/<YYYY-MM-DD>.md`（例: `.claude/logs/app-factory/2026-08-21.md`）。ファイルが無ければ作成する。

日付・時刻は必ずBashで取得すること（`date +%Y-%m-%d`、`date +%H:%M:%S`）。Workflowスクリプト自体は日時を扱えないため、ログの日時は呼び出されたエージェント自身がBashで取得する。

## 書き方

見出しレベル1つ（`###`）＋箇条書き（`- `）で1エントリ。既存の内容は書き換えず、末尾に追記するだけ。プローズの段落は書かない。

```
### [HH:MM:SS] <エージェント名>（補足があれば） — <一言サマリー>
- 結果: <何をした/どうだったか、簡潔に>
```

**成功側の記録は薄くてよい。** 問題なく完了した場合は上の「結果」1行で十分——長々と経緯を書かない。目的はログを後から読む人（主にユーザー）が「何が起きたか」を素早く追えることであり、正常系の詳細は読み飛ばされる前提でよい。

**問題・気づきがあった場合はここに厚みを持たせる。** バグを見つけた、指摘が出た、判断に迷った、次回以降に活かせそうな改善点に気づいた——こうしたケースでは`- `で始まる行を追加し、具体的に書く（目安3〜4行程度まで）。

```
### [HH:MM:SS] <エージェント名> — <一言サマリー>
- 結果: <簡潔に>
- 問題: <具体的に何が起きたか>
- 気づき/改善案: <次に活かせる点>
```

例（成功・薄い記録）:

```
### [14:02:11] idea-scout（レンズ: ビジュアル/作品性） — 候補5件を生成
- 結果: 「架空の美術館キャプションジェネレーター」など5件提案。既存項目との重複なし。
```

例（問題あり・厚い記録）:

```
### [14:18:40] design-qa-critic（ラウンド1） — 不合格。CSSバグを検出
- 結果: 不合格
- 問題: `.upload-section`のCSSが`[hidden]`属性を上書きしており、アップロード後もドロップゾーンが消えない
- 気づき/改善案: `[hidden]`属性に依存した表示切替は、CSS側で明示的に`[hidden]{display:none}`を上書きしていないか、prototype-builderが実装時にセルフチェックする項目に足すとよさそう
```

## 注意

- 凝ったものにしない。1エントリは数行で十分。
- 複数エージェントが並行して書き込むことがあるため、追記は1回のBashコマンドで完結させる（読み込んでから書き戻す、のような操作は避ける。`printf ... >> ファイル` のような単純追記にする）。
- ログは「何が起きたか追える」ことが目的の簡易記録であり、正式な成果物・仕様書ではない。ローテーションや削除は必要になったときに考える。

## 教訓（このスキル自体の運用について）

初回運用時、エージェントに「作業の最後にこのスキルの手順に従ってログを残す」とだけ指示したところ、エージェントは`Skill`ツールでこのスキルを呼び出して内容を読むところまでは実行したが、実際にBashコマンドを実行せずにそのままStructuredOutput（最終回答）を返して終了してしまい、ログが1件も残らなかった。`StructuredOutput`を呼ぶとエージェントのターンはそこで終わるため、ログ書き込みはそれより前に完了していなければならない。

この経験から、**呼び出し元のエージェント定義（`.claude/agents/*.md`）には、このスキルを呼び出させるのではなく、実行すべきBashコマンドをそのまま埋め込み、「最終回答を返す前に必ず実行すること」と明記する**運用にしている。スキルを読ませるだけの間接指示は、実行に繋がらないことがあるという教訓。
