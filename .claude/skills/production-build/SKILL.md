# production-build

sdd-managerは単発の仕様書駆動開発（1回のspecify→plan→tasks→implement→verifyサイクル）を実施するのに向いている。だが本実装の要件が複数の独立した機能にまたがる場合、sdd-manager単体には向かない。このスキルは、その分割と順序管理をメインセッション側で行うための手順を定める。sdd-manager自体の役割・使い方は変えない。

## 使うタイミング

- `.claude/CLAUDE.md`の開発フロー・体制ステップ4（制作移行）で、確定要件を見て「これは1つの仕様書には収まらない」と判断したとき
- プロトタイプ採用後の本実装で、プロトタイプの機能範囲を超えて複数機能を積み上げる必要があるとき

## 手順

1. **分割**: `feature-planner`エージェントに、確定要件（プロトタイプがあれば実装・コンセプトも含めて）を渡し、機能ごとの分割案（スコープ・依存関係・順序）を出させる。
2. **確認**: 分割案をユーザーに一言確認する。ここは進め方が大きく変わる分岐点なので、確認なしに決め切らない。
3. **順次発注**: 確定した順序で、機能を1つずつ処理する。並行には走らせない（後続機能は先行機能のコード・データモデルに依存することが多いため）。各機能について:
   - sdd-managerに、その機能**だけ**をスコープにして仕様作成〜実装〜自己検証までを依頼する（既存の開発フロー・体制ステップ4と同じ発注の仕方）
   - メインセッションが独立して検証する（ビルド・テスト実行・ブラウザでの実際の動作確認。既存の開発フロー・体制ステップ5と同じ）
   - 進捗はsdd-managerが持つTask機構（TaskCreate等）で機能ごとに管理する
   - 検証で問題が見つかった場合、次の機能には進まず、その場で対応してから先に進む
4. **完了**: 全機能の実装・検証が終わったら、`PROJECTS.md`のステータスを「完成」に更新する。

## app-factory（自律プロトタイピング）との違い

app-factoryはプロトタイプの自律生成に特化しており、完了までユーザーの介在なしに`Workflow`ツールで一気通貫に走る（失敗しても被害が小さいプロトタイプだからこそ許容できる自動化）。production-buildは実際に使われるコードを積み上げる工程であるため、あえて全自動化せず、機能ごとにメインセッションの独立検証を挟みながら対話の中で一つずつ進める設計にしている。
