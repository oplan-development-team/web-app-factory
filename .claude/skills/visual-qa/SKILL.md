# Visual QA

CSSを書いたことと、意図した見た目が実際に出ていることは別。「コードは正しく見える」で完了にせず、レンダリング結果を測って確認する。参照画像があるとき（`pixel-fidelity`）だけでなく、ゼロから独自デザインを作るとき（`frontend-design`）にも同じ精度で使う。

## 使うタイミング

- `frontend-design`で実装したあと、完了報告の前に必ず一度通す
- app-factoryのprototype-builder・design-qa-criticなど、参照画像を渡されない自律生成の文脈でこそ重要（人間のレビューを挟まずに完成としてしまうため、自分で裏取りする以外に品質を担保する手段がない）
- 「なんとなく薄い」「テンプレっぽい」といった主観的な違和感が出たとき、その違和感を具体的な数値の問題に変換するために使う

## 核となる姿勢

CSSのプロパティは「そう書いた」であって「そう見える」を保証しない。以下は典型的に乖離が起きる場所。

## チェック1: 主要なコンポーネントすべてに余白があるか（書き忘れの見落とし）

一部のコンポーネントだけ`padding`を書き忘れて、中身がコンテナの縁に詰まって見える不具合は、参照画像の有無に関係なく最も基本的で、最も見落とされやすい欠陥。スクリーンショットを一目見ただけでは気づきにくい——他のちゃんとした要素と並んでいると「まあこんなものか」で流してしまう。**「気になった箇所だけ」確認するのではなく、実装した主要なコンポーネント種別を機械的に全数列挙して確認する**のがこのチェックの核。

```js
[...document.querySelectorAll('.card, .panel, .button, button, .badge, input, textarea, .tag, .chip')].map(el => {
  const cs = getComputedStyle(el);
  return {tag: el.tagName, cls: el.className, padding: cs.padding};
})
```

`padding: 0px`が返ってきた要素は、フルブリード画像のような明確な理由がない限り疑う。文字・アイコン・フォーム欄など「中身」を持つ要素でpaddingがゼロなのは典型的な書き忘れで、見た目が「詰まって」「窮屈で」「未完成っぽく」見える最大の原因になる。

**目視での裏取り**: 洗い出した各コンポーネントを部分拡大し、コンテンツの端とコンテナの境界がぴったり接していないか確認する。接していれば、コード上「動いている」ように見えても視覚的には壊れて見える。

**実例（ユーザー報告）**: 家紋ジェネレーターの発展版アプリ（`kamon-composer`、別リポジトリ）で、初期実装時にコンポーネントのpaddingが抜けていて見た目がおかしい箇所があったとの指摘を受けた。参照画像の無い実装だったが、上記のように主要コンポーネントを機械的に列挙してpaddingの有無を確認していれば、実装直後に気づけた可能性が高い種類の不具合。

## チェック2: 境界線・仕切り線は「知覚できる」レベルのコントラストがあるか

`border`や`divider`を指定しても、地色との明度差が小さすぎると実質見えない。これは「バグ」として気づきにくい——コード上は正しいので、レビュー時にコードだけ読むと問題なしに見える。

```python
def relative_luminance(hex_color):
    hex_color = hex_color.lstrip('#')
    r, g, b = (int(hex_color[i:i+2], 16) / 255 for i in (0, 2, 4))
    def lin(c):
        return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
    r, g, b = lin(r), lin(g), lin(b)
    return 0.2126 * r + 0.7152 * g + 0.0722 * b

def contrast_ratio(hex1, hex2):
    l1, l2 = relative_luminance(hex1), relative_luminance(hex2)
    lighter, darker = max(l1, l2), min(l1, l2)
    return (lighter + 0.05) / (darker + 0.05)
```

- 本文の文字色 vs 背景: WCAG AA基準で4.5:1以上（小さい文字）/ 3:1以上（大きい文字・太字）
- 装飾目的の境界線・仕切り線: アクセシビリティ基準ではなく「意図通り視認できるか」が目的。目安としてコントラスト比1.4〜1.5以上、または相対輝度差にして地色から10〜15%以上離れていないと、紙のグレインやグラデーションのある背景では実質的に消える
- 同じ役割の色トークンが複数ある設計（例: 罫線用に薄い色と濃い色の2段階）では、**使う箇所ごとに「その背景の上で実際に知覚できるか」を確認してから選ぶ**。トークン名の响き（"rule" vs "rule-strong"）だけで選ばない

実装後、対象要素とその背景色をそれぞれ`getComputedStyle`で取得し、上記の関数で比を計算する。閾値を下回っていたら、より強いトークンに差し替える。

```js
const el = document.querySelector('.paper-panel');
const cs = getComputedStyle(el);
({border: cs.borderColor, background: cs.backgroundColor})
// 取得した2色をcontrast_ratio()に渡して検算する
```

## チェック3: UIチャンク（ボタン・ナビ・タグ・バッジ）にbody由来のタイポグラフィが漏れていないか

本文用に大きめの`line-height`（例: 1.6〜1.9）をbodyに設定するデザインは多いが、これが明示的にリセットされずボタンやナビリンクに継承されると、paddingを詰めても効果が薄いまま高さだけが不自然に大きくなる。

**症状**: 「paddingを減らしたのに見た目の高さがほとんど変わらない」「1行のラベルなのに縦に間延びして見える」

**確認手順**: 短いラベル1行だけを持つUI部品（ボタン、ナビリンク、タグ、バッジ、パンくず等）は、実装直後に必ず`getComputedStyle`で`line-height`を個別に確認する。

```js
const cs = getComputedStyle(document.querySelector('.nav-link'));
({fontSize: cs.fontSize, lineHeight: cs.lineHeight, padding: cs.padding})
```

`line-height`が`font-size`の1.5倍を大きく超えていて、かつ明示的にそう指定した記憶がない場合は、上位セレクタからの継承を疑う。短いUIラベルには基本的に`line-height: 1`〜`1.2`程度を明示するのが安全というのが経験則。

## チェック4: 「対称的であるべき装飾」は実際に対称にレンダリングされているか

パネルの四辺、カードの上下左右など、対称であることが意図の装飾要素は、片側だけ`padding`や`border`の指定が漏れていたり、疑似要素（`::before`/`::after`）の`inset`がずれていたりすると非対称になる。目視では見逃しやすいので、対角のpadding/marginの数値を並べて比較する。

## チェック5: スクリーンショットは「見る」のではなく「照合する」

実装後にスクリーンショットを撮ったら、ただ眺めて「良さそう」で済まさない。`frontend-design`のQuality Gateで挙げている項目（階層、リズム、奥行き、タイポグラフィ、配色、hover/focus/active状態）を1項目ずつ、スクリーンショットの該当箇所を指差しながら「これが根拠」と言えるところまで確認する。特に:

- 影・境界線・区切りがあるはずの箇所を`zoom`（部分拡大）して、実際に視認できるか確認する
- hover/focus/active状態は実際にその状態を発火させてスクリーンショットを撮る（コードを読んで「実装されているはず」で済まさない）
- 375/768/1440幅など複数幅で、崩れ・意図しない折り返し・要素の重なりがないか確認する

## チェック6: 色は「意味」を持っているか、それとも「そこにあるだけ」か

アクセント色や強調色を複数箇所で使っている場合、それぞれの箇所で本当にその強調が必要か再確認する。全部が強調されていると、実質どこも強調されていないのと同じになる。使用箇所の一覧を書き出し、削っても意味が通る箇所がないか点検する。

## チェック7: 祖先の`overflow: hidden`が子要素を意図せず切っていないか

`border-radius`とセットで祖先要素に`overflow: hidden`を使う構成（角丸カード、ページ全体を囲む台紙コンテナ等）では、ドロップダウン・ツールチップ・モーダル・大きめの`box-shadow`など、意図的にコンテナの外へはみ出す要素が静かにクリップされる。トップページのスクリーンショットだけでは気づけない——その要素を実際に開いた状態で確認しないと発覚しない。

**手順**: `overflow: hidden`（または`clip`/`auto`）を持つ祖先要素を洗い出し、その内部に絶対配置・固定配置の要素（ドロップダウン、ツールチップ、モーダル等）が無いか確認する。あれば、実際にその状態を発火させてスクリーンショットを撮り、切れていないか確認する。コード上「表示する処理は書いた」で終わらせない。

```js
[...document.querySelectorAll('*')].filter(el => ['hidden','clip'].includes(getComputedStyle(el).overflow))
  .map(el => el.className)
```

## チェック8: 短いダミーテキストだけで確認していないか

プレースホルダー的な短い文字列（「サンプル」等）だけで見た目を確認すると、実際の長いタイトル・長い名前が入った瞬間にレイアウトが壊れることに気づけない。余白・サイズが「短い文字列でだけ」偶然きれいに収まっているケースは多い。

**手順**: 主要なテキストが入る箇所（見出し・カード名・ラベル等）に、想定される最長ケース（実データの2〜3倍程度の長さ、改行を含む文字列）を一時的に流し込み、意図しないはみ出し・折り返し・省略記号の有無を確認する。

## チェック9: 画像は`object-fit`を指定しているか（引き伸ばし・潰れ）

固定の`width`/`height`枠に画像を収める場合、`object-fit: cover`等を指定し忘れると、初期値の`fill`が適用され元画像のアスペクト比が崩れて縦横に引き伸ばされる。取得・生成した写真素材ごとに縦横比がバラバラな場合に顕在化しやすい。

**手順**: 固定サイズの枠に入れている`<img>`要素の`object-fit`を確認する。

```js
[...document.querySelectorAll('img')].map(img => ({src: img.currentSrc, objectFit: getComputedStyle(img).objectFit}))
// objectFitが 'fill'（未指定時の初期値）のまま固定サイズ枠に入っているものを疑う
```

## チェック10: カスタムフォントは実際に読み込まれているか

Google Fonts等の外部フォントを指定しても、URLの綴り間違い・CORS・ネットワーク遮断で読み込みに失敗すると、警告もエラーも出ないままフォールバックフォントで静かに描画される。フォールバックはサイズ・字幅がまったく異なるため、フォント前提で決めた余白・行間・レイアウトが総崩れになりうる。

**手順**: `document.fonts`で実際の読み込み状況を確認する。

```js
[...document.fonts].map(f => ({family: f.family, status: f.status}))
// status が 'loaded' になっていないカスタムフォントは読み込みに失敗している
```

## 参照画像がある場合

このスキルの手順に加えて、色・寸法を参照画像の実測値と突き合わせる作業が必要になる。その手順は`pixel-fidelity`スキルを参照（このスキルは「実装が意図通りに見えているか」の一般的な検証、`pixel-fidelity`は「特定の1枚絵とどれだけ数値的に一致しているか」の検証で、役割が異なる）。

## 完了の基準

- 実装した主要なコンポーネント種別を機械的に列挙し、`padding: 0px`のまま放置されている中身入り要素がないことを確認した
- 境界線・仕切り線として意図した箇所は、コントラスト計算で知覚可能な水準にあることを確認した
- UIチャンク（ボタン・ナビ・タグ等）のline-heightを個別に確認し、body由来の値が意図せず漏れていないことを確認した
- `overflow: hidden`な祖先を持つドロップダウン・モーダル等は、実際に開いた状態でクリップされていないことを確認した
- 主要なテキスト箇所は、最長ケースを想定した文字列でも崩れないことを確認した
- 固定サイズ枠の画像は`object-fit`が指定され、引き伸ばし・潰れが起きていないことを確認した
- カスタムフォントは`document.fonts`で`loaded`になっていることを確認した
- スクリーンショットは「眺めた」のではなく、Quality Gateの各項目に対して具体的な根拠箇所を指せる状態で確認した
- 見つかった問題は実装に反映してから完了報告している（「気になったが直していない」状態で終えない）
