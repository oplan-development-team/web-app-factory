# Pixel Fidelity

参照画像に「似せる」ことと「一致させる」ことは別の要求。後者は目視では担保できず、実測でしか担保できない。このスキルは、渡された1枚絵を実測してコードの数値を合わせる手順を扱う。

**前提として`visual-qa`のチェック（境界線の知覚可能性、line-height継承、スクリーンショット照合など）は参照画像の有無に関係なく必要。** このスキルはそれに加えて「特定の1枚絵とどれだけ一致しているか」を検証する。

## 使うタイミング

- ユーザーが画像（ChatGPT Image等の生成モックアップ、Figmaのスクショ、既存サイトのキャプチャ等）を渡し、「この通りに」「完全に同じに」「寸分違わず」といった強い一致を要求したとき
- 一度実装して見せた後、「色が違う」「余白が違う」のように具体的な差分を指摘されたとき（＝目視ベースの実装では通らないという合図）

`frontend-design`・`visual-qa`と排他ではなく併用が前提。方向性・トーンの決定は`frontend-design`、実装が意図通り見えているかの一般検証は`visual-qa`、「渡された1枚絵とどれだけ数値的に一致しているか」の検証・是正はこのスキル、という役割分担。

## 大前提: 完全一致は本質的に近似である

生成AIが作ったモックアップ画像は、実在のCSSファイルから書き出されたものではない。「本来の設計値が何pxだったか」という正解は存在しない。したがって「画面幅◯pxで表示したら寸分違わず一致する」という意味での完全一致は原理的に主張できない。

できるのは、**画像のピクセルを実測し、一定のスケール前提のもとで比率を合わせにいく**こと。これは十分に高い精度を出せるし、「目視でそれっぽく作る」よりはるかに要求に応える。ただし、この限界（スケール前提はこちらが選んだ解釈であって抽出した事実ではない）はユーザーに明示しておくこと。

## 手順

### 1. 基準スケールを1つ決める

参照画像側とライブ実装側の両方で同じランドマークを測り、比率変換の基準にする。おすすめは本文コンテンツ幅（ナビバーやヘッダーの左右端など、ページ全体に効く安定した横幅）。

```python
# 参照画像側: 罫線や帯の水平方向の連続ダーク画素からコンテンツ幅を検出する例
from PIL import Image
img = Image.open('reference.png').convert('RGB')
y = 235  # 罫線が通っているとわかっているy座標
xs = [x for x in range(25, img.width-25) if sum(img.getpixel((x,y))) < 450]
print('content column:', min(xs), max(xs), 'width', max(xs)-min(xs))
```

```js
// ライブ側: 同じランドマークをDOMで測る
document.querySelector('.nav-band__inner').getBoundingClientRect().width
```

`scale = live_px / reference_px` を求めておく。以降のすべての比較はこの比を通す。

### 2. 色は「範囲」で取得し、単点サンプリングを信用しない

1点だけ`getpixel`すると、アンチエイリアス・JPEGノイズ・紙のグレインで簡単に外れ値を拾う。矩形範囲を切り出し、最頻色または極値（最も暗い/最も明るい画素）で判断する。

```python
def extremes(box, label):
    crop = img.crop(box)
    pixels = list(crop.getdata())
    darkest = min(pixels, key=lambda p: sum(p))
    print(label, 'darkest', '#%02x%02x%02x' % darkest)
```

**罠**: 文字の近くをサンプリングすると、インク色を「地の色」や「枠線」と誤認する（手順3参照）。サンプリング範囲は文字・画像の外側、無地の領域を選ぶこと。座標に自信がなければ先にグリッド線を焼き込んだ画像を書き出して目視確認してから座標を決める。

```python
from PIL import ImageDraw
crop = img.crop(box)
draw = ImageDraw.Draw(crop)
for x in range(0, crop.width, 25):
    draw.line([(x,0),(x,crop.height)], fill=(255,0,0))
    draw.text((x+2,2), str(x), fill=(255,0,0))
crop.save('debug_grid.png')
```

### 3. 参照画像上のボーダーの実在は「連続性」で確認する

「その座標が暗いから枠線がある」と即断しない。文字のストロークがたまたまそのx座標を通っているだけの可能性がある。**枠線なら、y方向に広い範囲でほぼ連続して暗いはず**。文字なら、文字がある行だけ暗く、行間では明るくなる（＝断続的）。

```python
def is_real_border(x, y0, y1, step=3, thresh=620):
    vals = [sum(img.getpixel((x,y))) for y in range(y0,y1,step)]
    dark_ratio = sum(1 for v in vals if v < thresh) / len(vals)
    return dark_ratio  # 0.9以上なら実在の線、0.1〜0.5程度なら文字インクの誤検出を疑う
```

平均輝度をx方向に走査し、周囲より一段低いプラトーがあるかを見る方法も有効（生成画像の枠線はソフトでエッジが緩いことが多く、二値化での検出は失敗しやすい）。実装側にそのボーダーを反映したら、実際に知覚できる強さになっているかを`visual-qa`のコントラスト計算で確認する。

### 4. 余白・サイズは「コンテンツ幅に対する比率」で比較する

生の px 同士を比べない。参照画像側・ライブ側それぞれで「対象の寸法 ÷ 手順1のコンテンツ幅」を計算し、その比率を突き合わせる。スクリーンショットツールの縮小率やビューポート幅の違いを自動的にキャンセルできる。

```
reference_fraction = 対象の高さ(参照画像px) / コンテンツ幅(参照画像px)
live_fraction       = 対象の高さ(ライブpx)     / コンテンツ幅(ライブpx)
ratio = live_fraction / reference_fraction   # 1.0に近いほど一致
```

`ratio`が1から大きく外れていたら、CSSの該当値を`1/ratio`倍して再ビルド・再計測する。これを`ratio`が概ね0.95〜1.05に収まるまで繰り返す。**乖離が想定より大きいときは、padding値だけをいじる前に`visual-qa`のline-height継承チェックを疑うこと**（このスキルの実例で、ナビ高さの乖離の主因はpaddingではなくline-heightの継承漏れだった）。

### 5. 目視の最終確認: スクリーンショットのスケールを参照画像に合わせる

数値が収束したら、最後に人間の目でも確認する。ブラウザのウィンドウリサイズが効かない環境では、CSSの`zoom`を一時的に当ててスクリーンショットの見かけ幅を参照画像のコンテンツ幅に合わせると、そのまま並べて比較できる。

```js
document.documentElement.style.zoom = String(1 / scale); // 手順1のscaleの逆数
```

比較が終わったら`zoom`は必ず元に戻す（本番のCSSに混入させない）。

## よくある誤り（実例）

- **文字インクを枠線と誤認する**: `.feature`ブロックに枠線があると判断して追加したが、実際はサンプリングした縦帯が本文テキストの左端ストロークを拾っていただけだった。手順3の連続性チェックをせずに単点の暗さだけで判断すると起きる。
- **枠線の色トークンを取り違える**: 薄い罫線用トークン（例: `--rule`）を、実際には濃いめの罫線用トークン（`--rule-strong`）を使うべき箇所に流用し、地色との明度差がほぼ無くなって「線が見えない」状態になっていた（`visual-qa`のコントラストチェックで検出できる類の問題）。
- **line-heightの継承に気づかず、paddingだけをいじって迷走する**: ナビの高さが参照画像比147%だった原因は、paddingではなくbody由来の`line-height: 1.85`がナビボタンに継承されていたことだった。

## 完了の基準

- `visual-qa`の完了基準を満たしている（このスキルはその上乗せ）
- 主要な色は参照画像から実測した値でCSSトークン化されている（目視の近似色ではない）
- 主要な寸法（少なくとも構造の骨格になる要素: ヘッダー高さ、ロゴサイズ、ナビ高さ、主要ブロックのpadding）は、手順4の比率で概ね±5%以内に収まっている
- ユーザーには、完全一致が実測ベースの近似であることと、実測した比率の結果（例: 「ロゴは参照画像比99.97%」）を具体的に報告している
