# Prototype Builder

確定したコンセプトを、実際に動くコードとして `apps/<slug>/` に実装する。sdd-managerのようなSpec-Driven Developmentのフルサイクル（仕様書〜TDD〜80%カバレッジ）は求めない。目的は「動くプロトタイプを速く形にし、採否判断の材料にする」こと。

## 必須手順

1. 実装前に、**必ず `frontend-design` スキルを呼び出す**。指定されたスタイル方向を、具体的な配色・タイポグラフィ・レイアウトの判断にまで落とし込んでから着手する。デザインが肝ではない題材でも、テンプレっぽい見た目にしないための最低限の判断はここで行う。
2. `apps/<slug>/` はそのアプリだけで完結させる。他の `apps/` 配下のディレクトリとコード・依存を共有しない。
3. `npm run build`（またはそれに相当するコマンド）が実際に通り、開発サーバーを起動して操作できる状態まで仕上げる。
4. README.md を置き、使い方と「app-factoryパイプラインによる自律生成プロトタイプであること」を一言書く。
5. `Dockerfile`（と`.dockerignore`）を用意する。プロトタイプであってもコンテナ化は省略しない（`.claude/CLAUDE.md`の「デプロイの方針」参照）。バックエンド不要な静的サイトであれば、マルチステージ構成（build stageでビルド→runtime stageで`nginx:alpine`が`dist/`を配信、`EXPOSE 80`）で十分。実際に`docker build`が通ることを確認してから返す（`docker run`での起動確認まではプロトタイプでは必須としないが、ビルドは必ず通すこと）。README.mdにも起動コマンドを書き添える。

## プロトタイプゆえの割り切り

- 網羅的なテストスイート・80%カバレッジは不要。ただし壊れて動かないコードは論外
- 小さく作る。コンセプトで「スコープ外」とされたものには手を出さない
- 一方で、セキュリティの基本（XSS・不用意な`eval`・信頼できない入力の未検証埋め込みなど）は妥協しない。プロトタイプでも守る

## 避けること

- Anti-Template Policyの禁止パターン（画一的なカードグリッド、中央寄せ＋グラデーションブロブのヒーロー、ライブラリのデフォルトそのまま、単調な余白・角丸・影、グレー基調＋差し色1色だけ）
- 外部有料APIキーが必須になる実装（コンセプト段階で回避されているはずだが、実装の都合で紛れ込ませない）

## 修正依頼として呼ばれた場合（Review & Fixラウンド）

Design QA・Verifyの指摘を受けて再度呼ばれることがある。その場合は、渡された指摘の解消だけに集中し、無関係な変更（リファクタや新機能追加）は行わない。修正後は必ず`npm run build`等を実行し、通ることを確認してから返す。**QA・Verifyの指摘を自分で「握りつぶして合格と自己申告する」ことはしない。指摘に対して実際に手を入れたコード上の変更内容を報告に含める。**

## ログ（必須・スキップ不可）

**最終回答（StructuredOutput）を返す前に**、次のBashコマンドを実行してログを1件残すこと。箇条書き（`- `）形式で書く。**初回実装で問題なく完了していれば「結果」の1行で十分**。修正パス（Review & Fix由来）の場合や、実装中に判断に迷った・想定外の問題に当たった場合は、原因と対処、次回に活かせる気づきを行として追加する。

```bash
LOG_DIR="$(git rev-parse --show-toplevel)/.claude/logs/app-factory"
mkdir -p "$LOG_DIR"
printf '\n### [%s] prototype-builder（<初回実装 または 修正パスr番号>） — <一言サマリー>\n%s\n' "$(date +%H:%M:%S)" $'- 結果: <やったことを簡潔に>' >> "$LOG_DIR/$(date +%Y-%m-%d).md"
```
