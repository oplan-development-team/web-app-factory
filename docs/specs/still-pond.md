# still-pond（凪の池）

## 目的
スマートフォンでの短時間の休息・マインドフルネス体験を求めるユーザーに向けて、端末の傾きに物理的に反応するフォトリアルな3D水面を提供する。既存の類似アプリ（`puddle-tilt`は2D・玩具的なトイ、`karesansui-composer`は静的な砂紋書き出しツール）にはない、リアルタイム3Dインタラクションによる禅のヒーリング体験を実現することが目的。

## スコープ
- 含む:
  - three.jsによるフォトリアルな3D水面シーン（PBRマテリアル、環境マップによる照明、ソフトシャドウ、Bloomポストプロセス）
  - 水面に浮かぶ蓮の葉・丸石等の小物オブジェクト（PBR質感、プロシージャル生成）
  - `DeviceOrientationEvent`のbeta/gammaを用いた傾き検知と、水面傾斜・波の移流・浮遊物の物理反応への反映
  - iOS 13+の`DeviceOrientationEvent.requestPermission()`によるユーザージェスチャー起点の許可フロー
  - 実行環境のfeature detectionに基づく3状態（iOS許可API必要／許可不要でセンサーあり／センサーなし）の判定と、状態に応じたオンボーディング文言・操作ヒントの出し分け
  - 許可拒否時・センサー非対応時のマウスドラッグによる疑似傾き入力フォールバック
  - 初回訪問時のオンボーディング画面（状態に応じた案内文＋許可要求ボタン）
  - 3Dシーン表示直後の短い操作ヒント表示（フェードイン→フェードアウト）
  - スマホ縦画面を第一優先としたレスポンシブレイアウト（縦持ち固定を基本とする）
  - Docker化（マルチステージDockerfile）と`deploy.json`によるGitHub Pages配信設定
- 含まない:
  - 音声再生・BGM
  - 画像/動画等の書き出し・共有機能
  - サーバーサイド処理・外部API通信
  - 外部3Dアセット・テクスチャ画像ファイル・HDRIファイルの読み込み（環境マップ・小物オブジェクトはすべてプロシージャル生成で完結させる）
  - ユーザーアカウント、進捗や設定の永続化（Cookie/LocalStorage含む）
  - マルチプレイヤー・複数ユーザー間の共有機能
  - スマートフォンの横持ち（landscape）表示の最適化

## 機能要件
- FR-1: three.jsで3D水面シーンをレンダリングする。水面マテリアルはPBRベースとし、反射・屈折、波紋を表現する法線マップ、環境マップ反射を持つ。
- FR-2: 水面に浮かぶ蓮の葉・丸石などの小物オブジェクトを、水面と同様にPBR質感で表示する。
- FR-3: 環境マップ相当の照明環境をプロシージャルに生成し適用する（外部HDRIファイルは使用しない）。トーンは穏やかな空・黄昏〜薄明かりとする。
- FR-4: シーン内の主要オブジェクトにソフトシャドウを適用する。
- FR-5: Bloom程度の控えめなポストプロセスを適用する。
- FR-6: 起動時、feature detectionにより実行環境を次の3状態のいずれかに判定する。
  - (a) `typeof DeviceOrientationEvent?.requestPermission === 'function'`が真となる環境（iOS許可API必要）
  - (b) (a)に該当せず、`'ondeviceorientation' in window`等でセンサーの存在が確認できる環境（許可不要でセンサーあり。Android等）
  - (c) (a)にも(b)にも該当しない環境（センサーなし。PC等）
- FR-7: 初回訪問時、FR-6の判定結果に応じて文言を出し分けたオンボーディング画面を表示する。いずれの状態でも「はじめる」ボタンを含める。
  - (a)の場合: 「『はじめる』を押すと、端末の傾きセンサー利用の許可を求める画面が表示されます。『許可』を選ぶと体験が始まります」という趣旨の説明を含める。
  - (b)の場合: 端末を傾けることで操作できる旨を説明する。
  - (c)の場合: マウスのドラッグ操作で体験できる旨を、案内画面の時点で明示する。
- FR-8: 「はじめる」ボタン押下時、FR-6で(a)と判定された場合、そのユーザージェスチャーの中で`requestPermission()`を呼び出す。
- FR-9: 許可が得られた場合（FR-6で(a)かつ`"granted"`の場合）、またはFR-6で(b)と判定された場合、`deviceorientation`イベントのbeta/gamma値を継続的に取得し、水面の傾斜、波の移流方向・速度、浮遊物の転がりに反映する。
- FR-10: 許可が拒否された場合、エラーでアプリを停止させず、マウス操作へのフォールバックを案内するメッセージを表示したうえで、マウスドラッグ入力モードに切り替える。
- FR-11: FR-6で(c)と判定された場合、許可要求UIを表示せず、自動的にマウスドラッグ入力モードで起動する。
- FR-12: マウスドラッグ入力モードでは、ドラッグの移動量を疑似傾き値として扱い、傾き検知モードと同様の水面傾斜・波の移流・浮遊物反応を再現する。
- FR-13: 3Dシーンの表示が完了した直後、FR-6の判定結果（および許可拒否によるフォールバックの有無）に応じた操作ヒント（傾き操作またはドラッグ操作を説明する短いテキスト）を、数秒間フェードイン→フェードアウトで表示する。
- FR-14: レイアウトはスマホ縦画面を基準にしつつ、768px・1440px幅でも表示が破綻しないレスポンシブ対応を行う（画面向きの取り扱いは非機能・制約を参照）。
- FR-15: 傾き入力値（beta/gamma、またはマウスドラッグ由来の疑似値）を、シーンが破綻しない範囲にクランプしてから反映する。
- FR-16: FR-6の静的判定（feature detection）で(a)または(b)と判定され、かつ(a)の場合は許可が`"granted"`だった場合でも、実際には`deviceorientation`イベントが一度も発火しない環境（例: `requestPermission()`が実機の許可ダイアログなしに自動で`"granted"`を返すデスクトップChrome、`'ondeviceorientation' in window`が`true`を返すが実センサーを持たないデスクトップFirefox等）を想定し、傾き検知モード開始から一定時間（既定2.5秒）以内に有効なbeta/gamma値を一度も受信しなければ、実行時に自動でマウスドラッグ入力モードへ切り替える。切り替え時は操作ヒント（FR-13）もドラッグ操作の案内に更新する。

- AC-2: (a)と判定される環境でオンボーディング画面を表示したとき、案内文に「『はじめる』を押すと端末の傾きセンサー利用の許可を求める画面が表示される」旨、および「許可を選ぶと体験が始まる」旨の説明が含まれる。

- AC-4: (a)と判定される環境で「はじめる」ボタンを押すと、`requestPermission()`がユーザージェスチャーのコールスタック内で呼び出される。

- AC-11: 3Dシーンの表示が完了した直後、環境に応じた操作ヒント（傾き操作またはドラッグ操作を説明する短いテキスト）が表示され、数秒後にフェードアウトして画面から消える。

- AC-13: 光源またはカメラの角度を変えてキャプチャした2枚のスクリーンショットを比較したとき、水面の法線マップに起因する波紋の陰影変化が視認できる。

## 異常系・エッジケース
- DeviceOrientationEventのpermissionが「denied」のとき: エラー表示やアプリ停止をせず、マウス操作へのフォールバック案内を表示し、以降の入力はマウスドラッグで受け付ける（AC-6）。
- センサー自体が存在しない/APIが未実装のブラウザのとき（FR-6の(c)、`requestPermission`メソッド自体が存在しない場合を含む）: 許可要求UIを一切表示せず、直接マウスドラッグ入力モードで起動する（AC-9）。
- 傾き値（beta/gamma）がNaN・null・undefinedを返したとき: その値は無視し、直前の有効な傾き値（初回は水平姿勢）を保持したまま描画を継続し、シーンが停止・フリーズ・欠落しない（AC-14）。
- `requestPermission()`がPromiseをreject、または呼び出し自体が例外をスローしたとき: 例外をキャッチし、denied時と同じフォールバック案内を表示する（AC-7）。
- ユーザーがオンボーディング画面で「はじめる」を押さずにページを離脱し、再訪したとき: 許可状態や進捗を永続化しないため、再訪時も再度オンボーディング画面から開始する。
- 端末を極端な角度（裏返し・真下向き等）に傾けたとき: 傾き反映値を一定範囲にクランプし、水面や浮遊物が画面外へ飛び出す、または物理的に破綻した見た目にならない（FR-15）。
- FR-6の静的判定では(a)や(b)に該当するが、実機の傾きセンサーを持たないためdeviceorientationイベントが実際には一度も発火しない環境（例: 許可ダイアログなしに自動で"granted"を返すデスクトップChrome、`'ondeviceorientation' in window`が`true`を返すデスクトップFirefox）のとき: 一定時間有効な傾き値を受信できなければ、実行時に自動でマウスドラッグ入力モードへ切り替え、操作ヒントもドラッグ操作の案内に更新する（FR-16, AC-25）。

## データ・API
外部API通信は行わない。全ての処理（3Dレンダリング、傾き検知、入力処理）はクライアントサイド（ブラウザ）内で完結する。サーバーへのデータ送信は発生しない。ユーザーデータ・設定・進捗の永続化（Cookie/LocalStorage/IndexedDB等）も行わない。環境マップ・小物オブジェクトのテクスチャ・ノーマルマップを含め、外部の画像ファイル・HDRIファイル・3Dモデルファイルの読み込みは一切行わず、すべてプロシージャル生成（three.jsのジオメトリ生成・シェーダー・Canvas/DataTexture等）で完結させる。

## 非機能・制約
- 技術スタック: Vite + TypeScript + Three.js（本体および公式addons: EffectComposer/UnrealBloomPass等のpostprocessing）。UIフレームワーク（React等）は用いず、フレームワーク非依存の構成とする。
- アセット調達方針: HDRI相当の環境マップは、three.jsの`RoomEnvironment`相当、またはグラデーション+複数ライトによる自前の疑似環境マップで代替する。蓮の葉・丸石は基本ジオメトリ（`ExtrudeGeometry`や自作カーブ等）とプロシージャルなノーマルマップ/テクスチャ（Canvas/DataTexture等）で表現し、外部テクスチャ画像ファイルは読み込まない。ライセンス管理・Dockerイメージ肥大化を避け、New_Service_Appの「単発・小規模」「自己完結」方針に合わせるための決定である。
- 画面向き: スマートフォンでは縦持ち（portrait）表示を基本とし、横持ち（landscape）表示の最適化は行わない（非対応で問題ない）。
- パフォーマンス: 4x CPU throttling相当のモバイル環境で、シーン描画中の平均フレームレートが30fps以上を維持すること。多段Bloomやスクリーンスペース反射（SSR）等の重いポストプロセスは避け、Bloom程度の軽量な後処理に留める。
- レスポンシブ: スマホ縦画面（375px相当）を第一優先とし、768px・1440px幅でも表示崩れが発生しないこと。
- 対応ブラウザ: モバイルはiOS Safari最新版・Android Chrome最新版、PCはChrome/Firefox/Safari最新版。
- Docker化: マルチステージDockerfileを用意する（build stageで`npm run build`を実行し、runtime stageで`nginx:alpine`等が`dist/`を配信する構成）。
- `apps/still-pond/deploy.json`に`{"pages": true}`を設定し、GitHub Pagesのサブパス配信に対応するため`vite.config.ts`の`base`を`'./'`にする。
- スタイル方向: 和のライトトーン・静謐な「間」を活かした構成とする（具体的な配色・タイポグラフィは実装フェーズで`frontend-design`スキルにより確定する）。
